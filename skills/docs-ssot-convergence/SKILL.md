# 文档体系 SSOT 收敛（Docs SSOT Convergence）

> **一句话**：先盘点文档角色，把"定义型内容"提取到一份 Markdown 总领文档（按 主线→支线→模块化 三视角组织），其他文档改造成"派生视图"（引用不重复），旧快照标注降级，最后用文档级场景走查把所有死角挖净。
>
> **适用**：方案文档+开发手册+说明并存、同一契约多处定义、改一处忘另一处（漂移）、"执行时全是问题"的项目。

## A. 核心流程（七步）

```
1 盘点 → 2 定载体 → 3 三视角重构 → 4 提取去重 → 5 降级标注 → 6 交叉核验 → 7 文档级走查
```

### 步骤 1：盘点文档角色

给每份文档贴角色标签，确认"谁该是定义源"：

| 角色 | 职责 | 典型 |
|---|---|---|
| 导航 | 只指路不定义 | README |
| 规则 | 约定/铁律（引用 SSOT） | AGENTS |
| **定义（SSOT）** | 唯一权威源 | 系统设计/技术方案 |
| 执行 | 任务书（引用不重复） | 开发手册 M1-M4 |
| 展示快照 | 评审/演示，降级标注 | HTML 方案/原型 |

### 步骤 2：定 SSOT 载体

- **推荐 Markdown**（可 diff/评审/维护）；HTML 只做展示快照，不做定义源
- 位置：`docs/系统设计.md` 或 `docs/总领文档.md`，README 文档索引置顶

### 步骤 3：三视角组织 SSOT（关键！不按实现流水账平铺）

| 视角 | 回答 | 组织方式 |
|---|---|---|
| **主线** | 系统做什么、数据怎么流动 | 用户旅程/数据流（如"一次卡片的生命周期"），每步只写"做什么+触发什么"，机制细节指向支线 |
| **支线** | 机制怎么工作 | 每条机制**自包含**（规则/存储/API/边界/里程碑），如 词表/权限/版本/并发/状态机/审批/通知/视图 |
| **模块化** | 怎么实现 | 分层铁律/模块文件清单/前端结构/**API 契约总表**/技术选型/里程碑交付表 |

> 反面教材：按"数据→版本→权限→检索→API→部署"平铺 = 实现视角流水账，主线不突出、支线散落、模块化缺失。
> 主线别写歪：主线 = 用户旅程，不是"从数据层到前端"的实现顺序。

### 步骤 4：提取定义 + 手册去重

- 定义型内容（数据模型/API/权限/规则）从旧文档提取进 SSOT
- 手册/AGENTS 改造成"引用 SSOT"，**删掉重复定义**（同一概念只许写一处）
- 改文档后维护链：CHANGELOG → AGENTS 基线 → 推送

### 步骤 5：旧文档降级标注

- 旧快照（HTML/旧方案）头部加注释：`以 docs/系统设计.md(SSOT) 为准，本文件仅展示/存档`
- 过时表述显式标注（如"评论绑定版本已过时，以 SSOT §2.3 为准"）

### 步骤 6：交叉核验（脚本化，别靠人肉）

| 检查 | 方法 |
|---|---|
| API 契约一致性 | 提取全部端点的 (方法,路径) 对，SSOT vs 手册 set 比对 |
| 术语统一 | 同一角色/概念只许一个叫法（如"工种负责人"非"栏负责人"） |
| 引用无断链 | grep 所有"§N/见 X"引用，目标必须存在 |
| 假引用 | 声称"X 已实现/留到 Y"，目标处必须真存在（审批结果通知/缩略图刷新留 M4/卡片改名——都是假引用坑） |
| data 目录对账 | 每个数据文件都有读 API + 写 API（CRUD 完整性） |

### 步骤 7：文档级场景走查（衔接 scenario-walkthrough 技能）

代码未写时走查**文档定义链**：`页面 → API → service → store → Git`，链路终点=定义；断裂=🔴。

**文档级走查重点（今天挖出的坑型，检查清单）**：

- [ ] **声明≠可操作**：每个"支持 X"必须有入口 API（图片上传/元数据编辑/关联增删——声明了没端点是 P-08/P-09/P-13 类）
- [ ] **写端点×版本语义真值表**：每个写端点必须回答 `commit? / +0.01? / 触发状态机? / 触发通知?` 四问（漏定义=执行期坑）
- [ ] **触发边界防无限环**：变更→通知 型机制，触发条件必须**白名单化**（只由内容提交触发），防副作用自触发（通知自身 commit 再触发订阅=无限环 P-21）
- [ ] **乐观锁粒度**：校验粒度必须与冲突资源一致（版本号是全局计数，校验粒度是文件——卡片级版本 vs 分工栏文件的矛盾 P-05）
- [ ] **状态机唯一入口**：禁止双入口（自动判定后又要求手动动作 P-01）；状态设置入口要定义（谁/何时 P-19）
- [ ] **失败态有恢复路径**：任何"失败/待处理"状态必须配套重试机制（P-06）
- [ ] **异步写原子性**：worker 异步写 vs git add -A 全量提交 → 原子写（临时文件+rename P-07）
- [ ] **高频状态与版本史**：所有 data/ 变更 commit 的取舍要显式决策（P-15）
- [ ] **建卡/初始值**：起始版本、slug 生成、id 规则等边界值要定义（P-20）
- [ ] **降级路径**：外部依赖（token/模型/API）缺失时的行为要定义（P-04）

## B. 沉淀规范

- 问题记入 `docs/09-pitfalls.md`（P 编号递增，格式：现象/原因/解决/预防/相关，状态 open→fixed→verified）
- 走查产物落 `docs/walkthrough/`（capabilities.md 能力清单 / scenarios.md 素材剧本+覆盖矩阵）
- CHANGELOG 加版本条目；AGENTS 基线同步；结论写入当日工作日志

## C. 经验教训（2026-08-18 knowledge-retrieval-system 实战）

- 7 轮走查 22 坑：状态机矛盾/乐观锁粒度/能力缺口（声明≠可操作）/版本语义全表/通知无限环
- 分散文档必然漂移：同一概念 4 处写岔（函数注释/原则/风险表/周任务各自写了一遍）
- 术语统一要趁早：栏负责人 vs 工种负责人，修一次牵 8 处
- 批量替换 hash 用精确串，勿用宽泛正则（曾误替换历史基线）
- 新克隆/损坏仓库处理：knowledge-base 类小仓库 .git 易损坏（rebase 中断）→ 备份改动后重克隆，配置 git 身份
