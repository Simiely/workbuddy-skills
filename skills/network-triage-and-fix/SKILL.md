# network-triage-and-fix —— 网络分层诊断与修复

职责：**本机网络问题的调研 → 定位 → 建议 →（等用户答复）→ 执行修复 → 同尺复验**。
铁律三条贯穿全程：不猜、不凭单次采样下结论、不在用户答复前执行有影响的改动。

## 适用场景

- 用户说"网络不稳定 / 卡 / 慢 / 时好时坏 / 上不了网"。
- 用户要求"体检一下网络"、"看看有什么要修的"。
- 特定站点/服务打不开（需区分 本机配置 vs 被墙资源）。
- 改完网络设置后要验证是否生效、是否引入新问题。

## A 主线（必做流程）

### 第 0 步　对齐口径：先测基线，再谈"稳定"

- 动作：`python scripts/bench.py --save before`（或当前时间标签），得到可比数字
  （30 域冷启动 / 国内 CDN 建连 / 境外建连）。
- 铁律：**"不稳定"必须用同一脚本、同一域名集复测对比**，才能区分"性能退化"与"主观感受/被墙资源"。
  每次只换一个变量。
- 产出：`bench_<标签>.txt`。

### 第 1 步　只读调研（零写入，`flushdns` 除外）

- 动作：`python scripts/triage.py` 全量采样；按需补专项（见 B 组各工具触发条件）。
- 采样内容：接口状态/跃点、默认路由、DNS 现状、链路质量（网关/DNS/公网各 30 包）、
  DNS 解析耗时、实时带宽（多段采样）、TCP 443 建连、TCP 状态统计（SYN_SENT！）、接口错误计数。
- 铁律：
  - **本阶段零写入**——任何"顺手修一下"都会污染现场。
  - 每条观察记下「命令 + 关键输出行」，报告里每条结论都要能溯源。
- 产出：分层实测数据。

### 第 2 步　三层归因定位

按 **解析 → 建连 → 带宽** 顺序逐层排除：

1. **解析层**：DNS 配置（静态单点？被覆盖？）、解析延迟、劫持检查（不存在的域名应返回 `rcode=3`，
   返回 0 = 被劫持到广告页）、CDN 调度质量（同一域名不同 DNS 解析出的 IP 建连耗时差可达 10 倍）。
2. **建连层**：TCP/TLS 到关键站点；**抓 `SYN_SENT` 找"卡住的目标"**——
   能连上 = 本机/应用问题；连不上 = 被墙或对端问题（用 IP 直连复核区分）。
3. **带宽层**：**单连接 + 多连接 + 多站点并发**三个口径一起测。
   只测单连接会被 CDN 的每连接限速误导（实测：阿里云单连接 0.87MB/s，4 线程 3.03MB/s；
   腾讯云单连接就是上限，并发不涨）。

铁律：
- **区分三类问题**，对策完全不同：
  - 真故障（断连/丢包/解析失败）→ 修配置
  - 配置卫生（代理残留、双默认路由同跃点、幽灵 WINS、僵尸接口）→ 清理，低优先级
  - **被墙资源（IP 级丢包 + SNI 级 RST）→ 换 DNS 救不了，只能代理、镜像或 fail-fast**
- **归因要设计对照组**，不能用总耗时直接归因某环节。
  （实测案例：NetBIOS 名字 15 字符上限——超过 15 字符 Windows 跳过 NetBIOS 段，
  用「短名 2781ms vs 超长名 1347ms」才切出 NetBIOS 段真实成本 ≈1.4s，
  而那 1.35s 的"基线"其实是 DNS 解析失败的固定耗时。）
- **单次采样不定论**：github 通道同一小时内"全通→全挂→全通"是常态；同一 IP 的 TLS 十分钟内可从通变全废。
- 区分"失败路径"与"成功路径"的耗时：失败耗时往往由最慢那段超时决定。
产出：问题清单（每条：现象 / 证据行 / 根因 / 影响量级）。

### 第 3 步　给建议，等答复（**不执行**）

- 动作：按 P1/P2/P3 列清单，每条给 **证据 / 在哪改（界面路径+命令）/ 收益 / 代价 / 风险 / 回滚方式**；
  并明确标出**"建议不动"**的项和理由（避免用户以为漏了）。
- 铁律：
  - **有影响的改动必须等用户答复。** 调研、备份、出报告不算影响。
  - **给建议前先实测当前状态**——用户可能已经自己改了
    （实测案例：用户 10:39 已自行删除 git 全局代理，若不查 `~/.gitconfig` 修改时间就会重复操作）。
  - 涉及"哪家快/哪家对"的选型（DNS/镜像/CDN），必须 **检索权威来源 + 本机实测** 双线验证。
    （本次验证修正 2 条：pip 镜像实测清华非最优 → 改阿里云；EEE 收益预期 → 实测无收益降级。）
  - 给"一键还原"类建议前**必须先看生成物内容**——
    `netsh -c interface dump` 不含 DHCP 网卡的 DNS、且正文带 `reset`（真执行会重置网络），不能当备份用。
- 产出：建议清单文档（含验证方法说明，透明标注每条用了什么验证手段）。

### 第 4 步　按用户选择逐项执行

- 动作：逐项执行。每项**执行前先 `python scripts/net_backup.py` 备份**；每步写日志并读回；改完必须复验。
- 铁律：
  - **掉网类操作（重启网卡/改路由）必须带自动回滚**：
    改值 → 重启 → 轮询等 Up（有上限，实测 15×2s）→ 没 Up 就写回原值再重启。
  - 需要管理员的走 `python scripts/run_elevated.py <bat> --marker <file> --wait 60`
    （B4 有两个"假成功"坑，必须遵守）。
  - 改网卡高级参数后**必须验证"重启后值有没有被驱动改回去"**（实测 Intel I219 接受了直写值）。
  - **执行前必须实测当前状态**——用户可能已自行修改。
  - 提权脚本的日志文件名必须与 cmd 重定向目标**错开**，否则 `Out-File -Append` 撞锁 → 日志 0 字节 → 误判"脚本没跑"。
- 产出：执行记录（每步 命令 / 结果 / 验证），并把建议文档对应项打上状态标记。

### 第 5 步　同尺复验 + 沉淀

- 动作：`bench.py --save after` 与第 0 步对比出表；更新 `net_backup.json`；
  把本次新坑写回本 skill 的 B 组与仓库 `DEVELOPMENT.md`。
- 铁律：复验必须包含"没被搞坏"的反向验证（例：改网卡后吞吐是否还正常）。
- 产出：对比表 + 更新后的备份 + 坑记录。

## B 工具库（按需查）

### B1　`scripts/bench.py` —— 同尺性能基准
触发条件：需要量化"改造前/后"、判断是否性能退化。
用法：`python scripts/bench.py --save <标签>`；输出 `bench_<标签>.txt`。
口径：30 个真实域名冷启动解析、4 个国内 CDN 建连、3 个境外域名建连。
**对比必须同脚本同域名集**，不同脚本/域名集的数字不可比。

### B2　`scripts/triage.py` —— 快速分诊（抓现场）
触发条件：用户报"不稳定/卡/慢"，第一件事就跑它。
输出：接口状态/跃点、默认路由、DNS 现状、链路质量（30 包）、DNS 解析、
实时带宽（4 段采样）、TCP 443 建连、TCP 状态统计（**SYN_SENT 单列**）、接口错误计数、网卡累计字节。
注意：网卡累计字节在网卡重启后会清零，勿与历史对比误判"流量倒退"。

### B3　`scripts/mirror_bench.py` —— 镜像源选型实测
触发条件：要推荐 pip/npm/软件镜像。
方法：**同一份数据**（如 `/simple/numpy/` 索引页 ≈1.3MB）在多家镜像间对比
建连+TLS、TTFB、传输速率。只测 TCP 建连测不出限速差异。
已验证结论（成都移动，2026-10-08）：npm 用 `registry.npmmirror.com`（官方源建连 1626ms vs 镜像 58ms）；
pip 响应优先阿里云（TTFB 107ms）、吞吐优先华为云；清华可用但非本机最优。

### B4　`scripts/run_elevated.py` —— 提权执行器（Windows）
触发条件：需要管理员改系统设置（DNS/路由/服务/注册表 HKLM/HKCU 受保护键）。
用法：`python scripts/run_elevated.py <bat> --marker <file> --wait 60`
**三个实测坑（必读）**：
1. **对 `.bat` 直接用 `runas` 动词 = 假成功**：`ShellExecuteW` 返回 42（>32 看似成功）但脚本根本不执行。
   正确姿势 = 把 bat 包进 cmd.exe：`ShellExecuteW(None,"runas", r"C:\Windows\System32\cmd.exe", '/c "<bat>"', None, 0)`。
2. **判成功只能靠"提权进程写标记文件 + 本进程回读"**，绝不能信 ShellExecuteW 返回值。
3. **PowerShell 工具里 `Start-Process -Verb RunAs` 会被安全策略拦**；提权脚本日志名必须与 cmd 重定向目标错开，
   否则 `Out-File -Append` 撞锁 → 日志 0 字节 → 误判"没跑"。
另外：`HKCU\...\Internet Settings` 这类"看起来不用管理员"的键，受限令牌下同样写不了（`WinError 5`），
加 `dangerouslyDisableSandbox` 也一样 —— 一律走提权进程。
掉网类操作在 PS 里按"改值 → 重启 → 轮询等 Up → 没 Up 写回原值"实现自动回滚。

### B5　`scripts/net_backup.py` —— 网络配置备份（安全）
触发条件：执行任何修复**之前**。
输出：`net_backup.json`（可编程恢复）+ `net_backup.txt`（人类可读快照）。
内容：各接口 GUID/IP/网关/静态与 DHCP DNS/NetBIOS、TCP 全局参数、默认路由、代理、网卡节能参数。
**别用 `netsh -c interface dump` 当备份**：不含 DHCP 网卡的 DNS、正文带 `reset`，真执行会重置网络（实测核验）。

### B6　沙箱 / Windows 实测坑清单
- **编码**：cmd 系工具输出 GBK → 一律 python `subprocess` + `.decode("gbk", errors="replace")`，别用中文 grep。
- **黑名单**：`reg.exe` 被沙箱安全策略拦截 → 读注册表用 python `winreg`（读 HKLM 可行，写要提权）；
  `tasklist`/`wmic` 也可能失败 → 查进程名用 python `ctypes`（`CreateToolhelp32Snapshot` / `QueryFullProcessImageNameW`）。
- **判网用 python urllib，不用 curl**（WorkBuddy 劫持 curl 致假失败）。
- **npm/pip 是 `.cmd`**：`subprocess.run(["npm",...])` 报 `WinError 2` → 用 `shell=True`。
- **`ls` 不显示点开头文件**：`.gitconfig.bak` 会"看不见"，用 `ls -a` 核验备份，别误判备份失败。
- **网卡的累计流量计数器在网卡重启后清零**，对比历史流量前先确认中间有没有重启过网卡。
- **`ipconfig /all` 里节点类型「混合」= h-node**：先查 WINS 再广播——若配了不存在的 WINS，
  单标签名解析会先干等它超时。

### B7　GitHub 资源通道矩阵（成都移动线路实测 2026-10-08）
| 通道 | 可达性 | 用途 |
|---|---|---|
| `api.github.com` | ✅ 109ms，**唯一全程稳定** | 取文件内容（`Accept: application/vnd.github.raw` 直接返回本体）、判仓库可见性 |
| `codeload.github.com` | ✅ 80ms，ZIP 端到端 200 | **仓库页面 Code → Download ZIP 走这里**（私有仓库已登录同样有效） |
| `github.dev` | ✅ 398ms | 网页版 VS Code（仓库页面按键盘 `.`） |
| `github.com` | ✅（git ls-remote 成功过；clone 时通时断） | git clone / 网页 |
| `raw.githubusercontent.com` | ❌ 黑洞级（TCP 要 20s 才连上，TLS 被 RST） | **别用**；网页 Raw/Download raw 按钮最终都跳这里 |
| 私有仓库判别 | 匿名 API 404 + 公开仓库列表无 + 全局搜索 0 → 私有 | 别把 404 当"仓库不存在" |

### B8　选型实测口径（反误导）
- **"哪家快"必须本机实测 + 检索权威来源双线验证**。本次双线验证纠正了 2 条建议
  （pip 镜像清华 → 阿里云/华为云；EEE 收益预期 → 实测无收益）。
- **DNS 调度质量 ≠ 查询延迟**：同一域名不同 DNS 解析出的 IP 建连耗时差 10 倍
  （移动本地 DNS 给省内 CDN 节点 2~3ms，公共 DNS 给外省 20~40ms）。
- **权威依据**（检索证实）：git 全局 `sslVerify=false` 被 Git CCM 官方文档标 "not recommended"（MITM 风险），
  正确做法 = per-host `http.<url>.sslVerify` 或装 CA；上行占满拖垮下行（bufferbloat / ACK 走上行），
  通用建议上传限速到总容量 70~80%；npmmirror 为当前官方国内 npm 镜像（旧 taobao 域名 2022 废弃）。

### B9　被墙资源的应对矩阵（换 DNS 无效，别浪费时间）
GitHub `*githubusercontent.com`（185.199.108~111.133）：3 个 IP 级丢包 + 1 个 SNI 级 RST。
应对：取内容走 **API**（B7）；整个仓库走 **Download ZIP / git clone**；浏览器体验走 **hosts 钉黑洞 fail-fast**
（把 avatars/raw/objects/gist/camo.githubusercontent.com 指到 0.0.0.0，让浏览器立刻失败而非干等 20~60s；
**注意：开代理访问 GitHub 时需临时移除这几行**）。npm/pip 改走国内镜像源从源头避开。

### B10　本机环境事实（换机器需重新采集）
成都移动园区网（`10.4.240.16/23`，网关 `10.4.240.1`）；出口带宽上限实测 **25~30 Mbps 上下行对称**
（4 路并发不叠加）；有线网卡 Intel I219-LM（索引 11，GUID `{62e943d5-...}`，驱动实例 0001）；
DNS：首选 `211.137.96.205`（四川移动）+ 备用 `119.29.29.29`（腾讯）；
本地 git 通道时通时断（直连与 7890 代理都要试）；`~/.git-credentials` 里的 token 已失效（401）。

## C 检查与沉淀

### 代码审查点（脚本报错/结果可疑时）
- [ ] 输出是否 GBK 乱码被误读？（用 python decode，别 grep 中文）
- [ ] `.cmd`/`.bat` 是否用了 `shell=True`？（npm/pip 直接 list 会 WinError 2）
- [ ] 提权是否真的执行了？（看标记文件内容，别信 ShellExecuteW 返回值）
- [ ] 日志是否 0 字节？（与 cmd 重定向目标撞名 = 写入失败）
- [ ] 备份文件是否真的存在？（`ls -a`，点开头文件默认不显示）
- [ ] 网卡累计计数器是否被重启清零？（对比历史流量前先确认）
- [ ] 结论是否用了对照组归因？（总耗时 ≠ 单环节成本）

### 流程合规点
- [ ] 第 0 步基线与第 5 步复验是否**同一脚本同一域名集**？
- [ ] 调研阶段是否零写入？
- [ ] 建议清单是否每条都有证据行 + 在哪改 + 回滚方式？是否等了用户答复？
- [ ] 执行前是否跑了 `net_backup.py`？每步是否写日志并读回？
- [ ] 掉网类操作是否有自动回滚？改完是否验证"值没被驱动改回去"？
- [ ] 是否区分了 真故障 / 配置卫生 / 被墙资源 三类？
- [ ] "哪家快"的选型是否检索 + 实测双线验证？

### 落盘规范
- 实测数据一律落盘（`*_out.txt`），报告引用文件名；脚本产物（备份 json / bench 报告）放工作目录，不留桌面。
- 新坑回写两处：本 skill 的 B 组 + 所属仓库 `DEVELOPMENT.md`（一坑一篇）。
- 机型的环境事实（B10）标注采集日期，换机器全部重新采集。
