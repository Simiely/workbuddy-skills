## 三、两次自我纠正（方法论价值最高）

### 纠正 1：把 1.36 秒错记成"NetBIOS 的代价"

利用 **NetBIOS 名字 15 字符上限**（超过 15 字符 Windows 跳过 NetBIOS 段）做对照实验：

| 名字 | 长度 | 走 NetBIOS | 最快耗时 |
|---|---|---|---|
| `FAKEHOST` | 8 | ✅ | 2781 ms |
| `NOSUCHPC` | 8 | ✅ | 2793 ms |
| `FAKEHOSTNAME1234567890` | 22 | ❌ | 1347 ms |
| `ANOTHERVERYLONGNAME9988` | 24 | ❌ | 1357 ms |
| `www.qq.com`（对照） | — | DNS | 137 ms |

**结论修正**：那 ~1350ms 是「DNS 解析失败」的基线耗时，与 NetBIOS 无关；
**NetBIOS 段是再叠加 ~1430ms**（2781−1347）。
→ 修 NetBIOS 只能省额外那 1.4s，省不掉基线。

### 纠正 2：pip 镜像推荐清华 TUNA —— 实测不是最快

同数据（numpy 索引页 1.3MB）对比 5 家：

| 镜像 | 建连+TLS | TTFB | 速率 |
|---|---|---|---|
| 阿里云 | **14ms** | **107ms** | 0.59 MB/s（该站单连接限速） |
| 腾讯云 | 45ms | 395ms | 1.43 MB/s |
| 华为云 | 144ms | 231ms | **2.22 MB/s** |
| 清华 TUNA | 136ms | 256ms | 1.21 MB/s |
| 官方 PyPI | 440ms | 875ms | 0.98 MB/s |

**结论修正**：响应优先选阿里云、吞吐优先选华为云；清华可用但非本机最优。

## 四、明确"不用修"的项（避免过度修复）

| 项 | 不修的理由 |
|---|---|
| NetBIOS 全接口启用 | 短名解析路径平时不触发（NAS 走 IP、上网走域名），日常影响 ≈0 |
| EEE 节能以太网 | 实测无延迟抖动（网关 50 包抖动 0.00ms），关闭无可测收益（已关，无害） |
| 无全局 IPv6 | 上游未下发前缀；实测无副作用（Windows 过滤 AAAA，无 Happy Eyeballs 回退） |
| ZeroTier 第二默认路由 | 跳数 10034，未抢占流量 |
| 百度 ICMP 4% 丢包 | 公网 ICMP 被限速，TCP 实测正常 |
| 4 个僵尸接口注册表项 | 无害 |
| `*githubusercontent.com` 被墙 | 被墙资源，换 DNS 无效（IP 级丢包 + SNI 级 RST 双重封锁） |

## 五、"不稳定"复诊（改完后用户再报卡）

复诊发现网络**优于基线**（30 域冷启动 113ms，比上午 181ms 更快），真正原因是
**Edge 浏览器 3~10 条连接卡在 SYN_SENT**，目标全部是被墙的 `185.199.108/110.133`（GitHub raw 段）——
打开的 GitHub 页面要加载 avatars/raw 资源，每页白等 20~60 秒超时。

**教训**：复诊先用同尺 bench 排除性能退化，再抓 SYN_SENT 找卡住的目标——
目标能连=本机问题；连不上=被墙/对端问题。被墙资源的体感是"卡但不报错"。
