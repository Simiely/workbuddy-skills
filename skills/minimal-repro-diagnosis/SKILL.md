# 最小单元链路诊断法(Minimal Repro & Chain Diagnosis)

> 一句话:不猜。先建**最小单元**复现 → 把流程**拆成更小的单元**逐步运行、对比特征差异 → **差异集中在哪步,根因就在哪步**,权威资料交叉验证后修复,全链路回归。

## 适用场景(触发条件)

- 「只还原一部分」「部分生效」「某功能效果不对」——**完整功能在,但输出有残缺/细节丢失**
- **链路环节多**(捕获→转换→存储→输出),数据在途中某一步被改/被丢
- 已多轮修复无效——停止猜,先建最小单元把链路拆开看数据在哪步变了
- 涉及**数据保真**问题(格式/属性/字段在转换中丢失、被规范化改写)

## 核心方法论(5 步闭环)

### 第 1 步:新建最小单元复现(先让问题"裸奔")

- 独立 HTML/脚本,**只含触发问题的最小代码路径**,不依赖完整应用、不污染真实数据
- 输入可编辑 + 一键运行;内置多个样例
- ⚠️ **必须用真实用户数据复现**——理想化样例经常复现不出问题(富文本案例:真实 Word 复制 html 42550 字才暴露,内置样例全绿)
- 输入框监听 paste 捕获**真实剪贴板格式数据**(如 `getData("text/html")`),让用户直接粘贴真实来源复现

### 第 2 步:拆解到更小的单元(每步可独立运行、可对比)

把完整流程拆成 N 步,每步一个独立函数 + 独立面板,输出**特征统计**:

- 统计维度(通用):长度 / 标签集合 / 属性集合(块数、内联数、CSS 属性名集合)
- 示例(富文本链路):S1 捕获 → S2 内联化 → S3 存储 → C2 包装 → C3 剪贴板写入 → C4 还原渲染
- 每步展示输入/输出摘要 + 统计,**一键跑完整链路**也支持

### 第 3 步:前后对比找 lost / gained(定位在哪步)

- 步骤 i-1 输出 vs 步骤 i 输出,计算特征差:
  - **lost**(上一步有、这一步没有)= 真问题!→ 该步就是根因位置
  - **gained**(新增)= 可能是正向变换(如内联化把 style 块属性搬进元素),**不算问题,别误报**
- 真实数据全链路跑一遍,看差异落在哪一步,再读该步代码找具体原因

### 第 4 步:定位 + 权威交叉验证(不凭经验下结论)

- 差异集中步 = 根因 → 读代码 + 写**最小实验**验证假设(如:怀疑 CSSOM 丢属性 → 10 行测试确认丢哪些、是否被改写)
- **结论必须以搜索到的可信资料为前提**(MS Learn / MDN / Chromium / 官方文档),检索交叉验证后再动手
- 涉及外部程序行为(如 Word 还原)时,做**对照实验/开关组合**让用户亲自验证反推,别只靠推断

### 第 5 步:修复 + 回归(最小改动、全链路验证)

- 修复范围最小化;同步更新诊断工具中的代码副本(保持与主代码一致)
- 回归:全链路样例 + 真实数据 + 项目自带测试(冒烟等)全绿
- 注意环境坑(见下),否则验证的是旧代码/假结果

## 关键工具:还原开关实验台(反推外部程序行为)

把链路输出特征做成**可开关组合**(每个特征一个 checkbox),组合 → 生成 → 复制到剪贴板 → 用户粘贴到目标程序对比。用户找到"与目标程序实际效果一致"的组合 → 反推出目标程序认什么、不认什么 → 代码保留策略确定。

示例(富文本):xmlns 命名空间 / StartFragment / body 属性 / mso-* 属性 / o:p 标签 / head XML / 默认 xmlns,7 个开关。

## 关键陷阱(实战经验,一条条踩出来的)

1. **检测工具本身会骗你**:`clipboard.read()` 返回**剥壳片段**(无 html/body 壳),body 属性"丢失"是 read() 形式所致、非真实缺失——**验证剪贴板内容用真实粘贴回读**(paste 事件 `clipboardData.getData`)或 copy 事件内 setData 回读;`readText()` 只拿文本
2. **CSSOM 序列化丢未知属性**:`rule.style.cssText` 只保留浏览器认识的属性——`tab-interval`/`text-justify-trim`/`mso-*` 全丢、`word-wrap` 被规范化为 `overflow-wrap`。需要字符串级处理(`textContent` 正则解析)时,绝不能过 CSSOM
3. **API 返回形式 ≠ 其他应用拿到的数据**:read() 的返回是"Chromium 重写后的片段",不代表 Word 等目标应用读到的 CF_HTML 原始数据
4. **服务静态缓存**:改动静态文件后必须重启服务,否则验证的是旧代码
5. **旧数据混淆**:修复只对新数据生效——旧条目/旧缓存会显示"没修好",先排除
6. **用户确认关键**:定位后让用户做对照实验/确认具体缺失项,别只靠自己推断收尾

## 实战案例(2026-08-26 clipboard-tool v0.6.12,富文本"还原部分")

- **现象**:Word 复制 → 工具存入 → 复制 → Word 粘贴,只还原一部分(基础格式在,细节缺)
- **拆 6 步**(S1 捕获→S2 normalizeRichHtml→S3 存储→C2 buildWordDoc→C3 剪贴板写读→C4 渲染):每步统计 style 块/内联属性/CSS 属性集合
- **对比定位**:
  - S2 lost[tab-interval, word-wrap, text-justify-trim] → 根因①:CSSOM `cssText` 剥 Word 私有属性(实测 6 属性只剩 2)
  - 修完 S2 后仍丢 body 属性 → 根因②:`<body>` 标签上的文档级设置不在 `doc.body.innerHTML` 里,必然丢
- **权威依据**:MS Learn《HTML Clipboard Format》aa767917(Fragment 是粘贴主体,body 在 Fragment 外)→ 双保险(body 属性内联段落元素)
- **验证闭环**:真实数据全链路 S2 lost[无] → 真实 Ctrl+V 粘贴回读 4997 字全保留 → 开关实验台确认「不勾 head XML + 其余全开」= Word 正确还原组合 = 当前代码输出

## 检查清单(用前对照)

- [ ] 最小单元已建(独立、可编辑输入、一键运行、含真实数据样例)
- [ ] 链路已拆成 N 步,每步独立函数 + 特征统计
- [ ] 每步前后对比输出 lost / gained(lost 才是问题,gained 需人工判定)
- [ ] 用真实用户数据跑全链路
- [ ] 差异步已读代码 + 最小实验验证假设
- [ ] 结论已用权威资料交叉验证(搜索)
- [ ] 外部程序行为已用开关组合/对照实验让用户确认
- [ ] 修复后:样例 + 真实数据 + 项目测试全绿;诊断工具副本同步
- [ ] 根因沉淀到项目文档(DEVELOPMENT 一坑一篇 / AGENTS / CHANGELOG)

## 与兄弟 skill 的分工

- **scenario-walkthrough**:走**代码逻辑链路**(函数调用/状态机/权限矩阵),静态分析——"逻辑通不通"
- **isolated-diag-page**:实测**运行环境与 API 行为**(浏览器权限/iframe/数据落盘写后读回)——"环境/API 行不行"
- **本 skill(minimal-repro-diagnosis)**:**数据在链路哪一步丢失/变形**(链路拆解 + 逐步对比 lost/gained)——"数据在哪丢的"
- 组合用法:环境/API 问题 → isolated-diag-page;逻辑问题 → scenario-walkthrough;**数据保真问题(还原不全/部分生效)→ 本 skill**;复杂问题三件套叠用

## 反模式(避免)

- ❌ 不建最小单元直接猜/改主应用(补丁叠补丁)
- ❌ 只用理想化样例(真实数据才能复现)
- ❌ 把 gained(正向变换)当问题误报
- ❌ 用 read() 等"重写形式"API 验证数据(要用真实接收端验证)
- ❌ 不查权威资料就下结论
- ❌ 修复后不回归全链路 + 项目测试
